# 成本工程（COST ENGINEERING）

**播放视频不花钱，花钱的是"把内容变成笔记"和"看板书"。** 这份文档讲怎么让这两件事**花得可控、看得见**。

## 一、钱花在哪：三个量级

以 deepseek-flash 空闲时段价（输入 ¥1/百万 token、输出 ¥4/百万 token）估算：

| 动作 | 量级 | 成本 |
|---|---|---|
| 消化一篇 15 分钟视频的转写（约 5k 字符） | ≈ 3.5k + 12k 固定开销 输入 | **≈ ¥0.02** |
| 消化一篇 45 分钟视频的转写（约 45k 字符） | ≈ 44k 输入 + 2.5k 输出 | **≈ ¥0.05** |
| 读一张板书帧（1280×720） | ≈ 1300 token 输入 | **≈ ¥0.0013** |
| 读 40 张板书帧 | ≈ 52k token 输入 | **≈ ¥0.052** |

**实测对照**：一次真实的"消化 + 写笔记"跑完，用账号账本差值量出来约 **¥0.04**（与上表同量级）。

> 关键直觉：**图比同长度文本贵得多**。所以"多看几张板书"是最容易悄悄吃掉预算的动作——
> 这也是为什么读图必须过闸门，而文本消化反倒不用太紧张。

## 二、为什么不能只看余额

账号余额有三个问题：

1. **是账号级的**：混着你平时的对话、别的工具、别的会话——它变少了不代表学习这摊花的
2. **滞后**：余额由客户端轮询更新，短任务结束时还没刷新
3. **不可归因**：花了 ¥0.04，你没法知道是哪一篇、哪一次读图花的

所以本工具**自建账本**，把"学习这摊"单独记账。

## 三、双轨记账（这是核心设计）

```
        事前（预估，防止超支）                事后（实测，校准预估）
   ┌──────────────────────────┐      ┌──────────────────────────┐
   │ 转写一落盘 → 预约一份消化  │      │ 打点 begin … 跑任务 … end │
   │ 读图前 → 按张数预约        │      │ 取账号账本增量 = 真实花费 │
   └──────────────────────────┘      └──────────────────────────┘
                    ↓                              ↓
              committed = 预估占用 + 实测累计
                    ↓
         committed ≥ 上限 → 停止新增（而不是"超了再说"）
```

- **只靠事前预估**：模型可能话多，实际花费飘
- **只靠事后实测**：等你发现超支时钱已经花了，而且"还没消费的转写"没有计入
- **两条腿**：预估负责**拦截**，实测负责**校准**——两者都记进同一个账本（`data/spend.json`）

命令：

```powershell
bili-learn spend                       # 今天用了多少、每笔是什么
bili-learn frames --pick --want 6 --book   # 读图前预约（kind=vision）
bili-learn spend --clear-vision        # 读完撤销
```

在 DSH 环境里还能自动读账号账本（`doctor` / `spend` 会显示余额与今日总消费），
非 DSH 用户手动 `spend --add-yuan 0.05` 记录即可，**闸门逻辑完全一样**。

## 四、额度不足时的降级顺序（质量优先）

钱不够时，**先砍可降级的，不要先砍质量**：

| 优先级 | 动作 | 理由 |
|---|---|---|
| 1 | 减少读图张数（`--want` 自动降级，按"在场最久"保留最关键的） | 帧与帧之间有冗余，少读几张损失可控 |
| 2 | 少消化一篇（转写留着**不花钱**，明天继续） | 转写是资产，笔记可以延后 |
| 3 | 分段消化长转写（先提炼再合并） | 降低单次上下文压力 |
| 4 | 明确拒绝并告诉用户"余量 0，先等明日重置" | **绝不静默超支** |

第 4 条最重要：**闸门必须能说"不"**。一个"额度不足时会警告但仍然照做"的闸门，等于没有闸门。

## 五、几个实测得到的反直觉结论

1. **长上下文的第一代价不是钱，是注意力**。实测一次会话的**缓存命中率 99.2%**——长前缀被缓存复用，
   输入价格便宜到可以忽略；真正的风险是信息被稀释（中段细节丢失）。
   所以"省 token"不该是我们最优化目标，**"该看的信息有没有看到"才是**。
2. **峰谷差价值得排期**。官方口径：工作日 09:00–12:00、14:00–18:00 为高峰，其余时段（含周末与节假日）价格减半。
   把"要花钱的批量任务"排到空闲时段，成本直接砍半。
3. **打点会过期**。`begin` 之后如果隔了很久才 `end`，会把中间所有别的消耗误记成本次任务的花费
   （实测把 `measuredYuan` 顶爆过）。修法：打点带时间戳 + 设有效期（如 2 小时）+ 提供维护命令清零误记。

## 六、把这条经验带走

如果你要做自己的"AI 学习"工具，成本上只需要三件事：

1. **事前算钱**（而不是事后看余额）——每个动作都有可估的单价 × 数量
2. **独立账本 + 硬闸门**——把"这摊业务"和"账号总消耗"分开，闸门必须能拒绝
3. **降级有优先级**——先砍可再生的（张数/篇数），后砍不可再生的（质量/完整性）
