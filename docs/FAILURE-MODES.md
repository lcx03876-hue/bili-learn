# 踩坑表（FAILURE MODES）

这份表是这个项目**最值钱的部分**：开心路径（开浏览器 → 取字幕 → 总结）大概两百行就写完了，
真正花掉时间的是下面这些"看起来能用、其实在骗你"的失败模式。

每条格式：**现象 → 真因 → 修法**。凡是没有验证过的推断，都明确标成"怀疑"。

---

## 一、内容获取

### 1. 服务端直连 B 站 API 一律返回 412 / 空数据
- **现象**：Node 里 `fetch('https://api.bilibili.com/x/web-interface/view?bvid=...')` 拿到的是 HTML 反爬页
- **真因**：B 站对无浏览器指纹、无 cookie 的服务端请求做了风控（412）
- **修法**：**所有请求在页面上下文里发**（`Runtime.evaluate` 里 `fetch(..., {credentials:'include'})`），
  自带登录态与来源；顺带绕过 wbi 签名问题

### 1b. 已登录也未必够：**未登录**的干净 profile 会全线 412
- **现象**：全新的 profile 里，`view`、字幕等接口全部返回 412（HTTP 状态 412，内容是 HTML 反爬页）
- **排除过的假设**：不是"页面源不对"（首页/搜索页/视频页都试了）、也不是"指纹 cookie 没下发"
  （实测 `buvid3/buvid4/b_nut` 都在，仍然 412）、预热等待也无效
- **真因**：B 站对**未登录**的自动化访问拦得更狠
- **修法**：把"先登录"当成前置条件，并在代码里对 `-999/-412`（解析失败/风控）**给出明确指引**
  （"先跑 login"），而不是抛一句 `Failed to fetch`
- **顺带**：`fetch` 在 `about:blank` 上会因为**源不对**直接 `TypeError: Failed to fetch`——
  所以 attach 之后要先确认 `location.href` 落在 `bilibili.com`，否则先导航过去

### 2. 拿到字幕 ≠ 学完了：字幕轨常常只覆盖前几分钟
- **现象**：一条 33 分钟的视频，转写文件读起来"讲得挺完整"，但最后一行时间戳只到 `[00:08:06]`
- **真因**：AI 字幕轨是按"识别到语音的片段"生成的，**可能远短于视频长度**；也可能是 UP 只上传了片段
- **修法**：写完转写先算 **覆盖率 = 最后一行时间戳 ÷ 视频时长**，低于 80% 在文件头打 ⚠️ 并写进待办清单。
  > 反例也要防：8:06 对一条 8:08 的视频就是 99%——**先算比例再下结论**，我们一度把正常的当成"被截断"

### 3. 番剧/独家稿件：播放器永远 ready，等 45 秒超时
- **现象**：`waitFor('video.duration > 0')` 一直超时；页面标题正常、播放器容器也在
- **真因**：这类稿件会 **302 到 `/bangumi/play/...`**，而它是**大会员专享**——非会员只有"试看"
- **量化**：实测试看片段的 `duration` 恰好 **360 秒（6 分钟）**，之后播放器 `readyState` 停在 0
- **修法**：跳转后立刻检查 `location.href` 是否含 `/bangumi/`，是则**秒判不可播**并跳过（别空等）；
  选片阶段用 view 接口的 `redirect_url` 字段提前过滤

### 4. 没有字幕的视频会静默降级成"学了个寂寞"
- **现象**：转写文件只有标题和简介
- **修法**：选片时硬过滤"必须有字幕轨"；确实无字幕的明确记录原因，而不是产出一篇空笔记

## 二、播放与抓帧

### 5. B 站会记住播放位置 → "假覆盖"
- **现象**：一条 6 分钟视频的抓帧报告说 `watched=890s`，但墙钟只过了 27 秒
- **真因**：登录态下 B 站自动续播到上次位置，程序以为"从头看到了尾"
- **修法**：抓帧路径一律 **`restartFromZero`**（检测到 `currentTime > 2` 就 seek 回 0）

### 6. 定时全存抓帧会把磁盘吃满
- **现象**：一夜 755 张、118 MB
- **修法**：**按画面变化抽帧**——每 `sampleMs` 采 32×18 灰度缩略图算平均绝对差，超过阈值才存全分辨率；
  再加 `maxFrames` 上限、保留期、总量上限（并保护最新一个目录不被清空）

### 7. `maxFrames` 与"覆盖范围"是两件事（很容易配错）
- **现象**：调大 `maxFrames` 只让开头几分钟更密，后半小时一张没有
- **真因**：`minGapMs` 才是覆盖的决定项——40 张 × 8 秒 = 只能覆盖 5 分钟
- **修法**：`minGapMs = max(配置值, 时长 ÷ maxFrames)`，**帧数不变、成本不变，自动铺满全片**

### 8. 选择"读哪几张图"要比均匀抽样聪明
- **修法**：用**在场时长**（下一张时间戳 − 这一张）排序——停留越久越可能是完整板书；
  过渡动画/鼠标移动的中间帧在场极短，跳过它们省下的是真金白银的 vision token

### 9. 一个坏掉的标签页会让整晚"全灭"
- **现象**：连续 6 条视频都 `waitFor timed out: video ready`，但换一个新标签页打开**同一个视频** 3 秒就正常播放
- **真因**：同一个 tab 反复导航后进入坏状态（SPA 状态残留），每次失败要干等 45 秒
- **修法**：失败一次就**换新标签页重试**；连续 3 条失败则**冷却 10 分钟**（同时防被限流）；
  诊断脚本自己也要 `try/finally` 关掉它开的标签页

### 10. 抓帧与播放抢资源（**怀疑，未验证**）
- **现象**：20 次播放里 12 次 `stalled`（几秒就卡住），日志显示卡住前 10 秒内常有截图动作
- **状态**：时间上有相关性，但**没做对照实验**（关掉抓帧跑同样视频）
- **如果成立**：把 `sampleMs` 调大、或把抓帧挪到独立进程/事后离线抓
- **处理方式**：写在文档里当"待验证"，不当结论用

## 三、运行与自动化

### 11. "设置自动"≠"验证过自动"：计划任务创建完 `NextRunTime` 为空
- **现象**：改了计划任务后整晚没跑；手动触发一切正常（`LastTaskResult: 0`）
- **真因**：用了 `Once @ 02:30 + 重复 4 小时`，而创建时刻已是 19:04 —— **起点在过去、重复窗口已过期**，
  Windows 认为不会有下一次
- **修法**：正确写法是 **`Daily + 挂 Repetition`**，不是 `Once + 过去的起点`；
  验收必须看 **`NextRunTime` 非空**，并**让任务自己触发一次**（手动触发只证明"能跑"，不证明"会自己跑"）

### 12. 交互式任务跑控制台程序 → 每 10 分钟弹一次黑窗
- **真因**：`node.exe` 是控制台程序，Task Scheduler 在用户会话里跑它就弹窗
- **修法**：用 `wscript.exe` + 一个隐藏窗口启动器（`WshShell.Run(cmd, 0, False)`）；
  ⚠️ VBS 里的注释**必须纯 ASCII**（按系统代码页解析，UTF-8 中文会报语法错并弹对话框）

### 13. Windows PowerShell 5.1 按 ANSI 读 `.ps1` → 中文注释变乱码、语法报错
- **现象**：一个每天正常跑的脚本，被编辑器改过一次后突然全项目 08:00 的任务失败
- **真因**：编辑器**剥掉了 UTF-8 BOM**；5.1 无 BOM 时按 ANSI 解码，中文注释里的字节组合破坏了语法
- **修法**：`.ps1` 保留 **UTF-8 BOM**；改这类文件**不要用 shell 管道往返**（`Get-Content | Set-Content` 会剥 BOM
  或加 BOM），用编辑器或 `[IO.File]::WriteAllText(path, text, UTF8Encoding($true))`；文件头写注释提醒后人

### 14. 看门狗"救活"的进程可能永远不会收工
- **现象**：用户早上发现"昨天的视频还在放"
- **真因**：收工逻辑由环境变量（如 `DSH_BILI_SHUTDOWN=1`）控制，而看门狗 spawn 时**没带上它** →
  进程永远不会关窗口、不会退出，成为常驻僵尸（实测活了 32 小时）
- **修法**：所有拉起进程的地方**共用同一份环境契约**；进程启动日志里打印当前模式，便于一眼核对

### 15. 只拦"不能再开新视频"，拦不住"已经在播的那条"
- **现象**：到达窗口结束时间后，视频一路播完（可能超出窗口很久）
- **修法**：把"是否还在允许时段"作为**播放循环内的停止条件**传进去（`shouldStop`），窗口一到点即停；
  状态保留为"未看完"，下次继续——而不是标记失败

## 四、账与数据

### 16. `git add -A` 把 118 MB 抓帧图扫进了仓库
- **现象**：提交后仓库 113 MB；同一次还用 shell 往返改坏了 `.gitignore` 的编码，
  导致**登录态目录 `profile/` 失去忽略**（差点把 cookie 提交上去）
- **修法**：① `add -A` 前先统计范围（文件数 / 最大文件 / 扩展名），二进制产物一律进 `.gitignore`；
  ② 改 UTF-8 文本用编辑器而不是 shell 管道；③ `.gitignore` 改完必须
  `git check-ignore -v <关键路径>` 验证；④ 已误提交：`git reset --soft HEAD~1` +
  `git reflog expire --expire=now --all` + `git gc --prune=now`

### 17. 记账打点过期 → 把整个会话的消耗误记成一篇文章的成本
- **现象**：`measuredYuan` 突然被顶爆
- **修法**：打点带时间戳并设有效期（例如 2 小时）；提供 `repair-cost` 这类维护命令把误记清零；
  **每次操作前先算钱**，而不是事后看余额

### 18. 预估占用与实际花费必须两条腿走路
- **修法**：见 [`COST-ENGINEERING.md`](COST-ENGINEERING.md)——真实差值（事后）+ 预估占用（事前）双轨，
  只靠任何一条都会失真

## 五、配置与本地数据（Windows 上特别容易踩）

### 19. 记事本写的 BOM 让 `JSON.parse` 抛错 → 用户手工编辑的配置**被静默重置**
- **现象**：给 `config.json` 加了一个自定义键，跑一条命令后键没了，配置回到默认值
- **真因**：Windows 记事本、PowerShell 的 `Set-Content -Encoding UTF8` 写出的文件带 **UTF-8 BOM**；
  而 `JSON.parse('\uFEFF{...}')` **直接抛错**（`Unexpected token`）→ 代码在 `catch` 里回退成默认配置 →
  下一次写回就把用户的配置覆盖掉了。**全程没有任何报错**，这才是最毒的地方
- **修法**：读 JSON 的地方统一剥掉首个 BOM（`if (text.charCodeAt(0) === 0xFEFF) text = text.slice(1)`）；
  别在 `catch` 里把"解析失败"和"文件不存在"当成同一件事
- **顺带**：写回配置时若检测到 BOM 也建议顺手去掉（我们写出去的是无 BOM UTF-8）

### 20. 浅合并默认配置 → 之后新增的嵌套键永远 `undefined`
- **现象**：日志打印 `每 undefinedms 采一次`；改了配置文件里的新键完全没反应
- **真因**：`{ ...默认配置, ...文件配置 }` 只能合并**顶层**——文件里已有 `frames` 对象时，
  默认值里同名的整个 `frames` 会被**替换**，于是新增的 `frames.intervalMs` 永远是 `undefined`
  （`createFrameGrabber` 只好用它自己的默认值，看起来"能跑"）
- **修法**：**深合并**（逐层合并对象，数组按整体替换）；并且把合并结果写回文件，
  让新增配置项在文件里可见
- **同类坑**：配置键名必须和库参数**逐字一致**（我们曾用 `sampleMs`，而抓帧器要的是 `intervalMs`——
  用户改了配置，程序却读了另一个键）。改名时至少加一行注释说明对应关系

## 六、与库对接（"看不见的契约"）

### 21. 猜库的返回形状 → 用户可见输出里冒出 `NaN` / `undefined`
- **现象**：`login` 打印「二维码已存到 …（元素 **NaN×NaN**）」
- **真因**：`captureLoginQr` 实际返回 `{ file, clipped, selector }`，我按 `{ file, width, height }` 用了。
  `Math.round(undefined)` 就是 `NaN`，而模板字符串**不会报错**，于是静默输出垃圾
- **修法**：① 调库函数前先看它的 `return`（读一行就够）；② **凡是要打印外部返回值，先 `Number.isFinite` 校验**；
  ③ **输出里出现 `NaN/undefined` 就是契约没对齐的告警**，别当小瑕疵放过
- **同源教训（同一轮实测抓到的）**：`login` 用的是 `attach` 而不是 `attachBili` → 新标签页是 `about:blank` 源，
  页面内 fetch 被 CORS 拒 → `loginState` **永远**返回"未登录"，于是**每次 login 都白弹一次二维码**。
  "源不对"这类错会伪装成业务错（见 1b），而正确做法只有一条：**所有走页面内 fetch 的命令都必须先确保落在目标源上**

## 用法建议

如果你要基于这份表做自己的工具，最有价值的三条是：

1. **先验证内容完整性**（覆盖率），再谈总结质量
2. **失败要能区分"稿子的问题"和"环境的问题"**（换标签页重试 vs 直接标记不可播）
3. **所有"自动"都要有可观测的验收证据**（`NextRunTime`、心跳文件、进程模式日志）
